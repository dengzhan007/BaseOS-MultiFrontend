# RG34XX BaseOS 多前端内测使用指南

> **适用设备：** Anbernic RG34XX（Allwinner H700）  
> **适用版本：** `test/rg34xx-multi-frontend` 测试分支构建  
> **文档性质：** 内测说明，功能和操作细节可能随测试版更新  
> **重要提醒：** 本分支仍处于内测阶段。刷写完整镜像会重建 TF1 分区；操作前备份 TF 卡。CI 构建通过不等于所有功能已完成实机验收。

## 1. 这个版本与原版 BaseOS 有什么不同

原版 BaseOS 的定位是轻量系统底座：负责设备启动、硬件运行环境和启动一个前端。它本身不提供完整的游戏前端，也不负责在多个前端之间进行管理。

本测试版保留 BaseOS 的底座思路，在此基础上增加 RG34XX 多前端管理：

| 项目 | 原版 BaseOS | 本测试版 |
|---|---|---|
| 前端启动 | 以单个前端为主要使用方式 | 可发现、选择和管理多个前端 |
| 启动选择 | 启动已安装/配置的前端 | 开机按住 L1 或 R1 进入前端选择器 |
| 前端配置 | 由前端自身管理 | 支持同一前端建立多个独立 profile |
| 第三方前端适配 | 主要依赖前端自身适配 BaseOS | 增加自动兼容层，尽量不修改前端原始文件 |
| 目录布局 | 通常沿用前端自己的目录名 | 通过路径映射兼容不同目录命名，并提供统一共享目录 |
| 游戏库 | 由前端自行定位 | 规范游戏目录为 `Games/`，旧前端目录名可映射到它 |
| 配置与状态 | 由前端自行保存 | 收藏、最近游玩、前端设置等可按 profile 隔离 |
| 诊断界面 | 沿用对应版本的基础诊断能力 | 增加多前端入口、按键测试和 USB 存储入口等控制中心功能 |

### 1.1 保持不变的部分

本测试版仍以 RG34XX 原有 H700 启动链、U-Boot、内核、设备树和硬件驱动为基础。多前端管理主要由 BaseOS 用户空间程序、兼容包装器和控制中心实现。

目标是让前端尽量保持原样：BaseOS 在启动时识别其目录结构和启动入口，按需建立兼容配置及临时路径映射，而不是要求每个前端都加入 BaseOS 专用代码。

### 1.2 当前测试范围

目前重点测试：

- 前端自动发现、启动和默认项设置；
- 同一前端的多个 profile；
- 第三方前端的自动兼容与卸载边界；
- ROM、存档和素材目录的共享/隔离；
- 前端路径映射及退出后的清理；
- 诊断控制中心、按键测试、语言切换和 USB 存储；
- A/B 系统升级。

不同前端的模拟器、核心、按键、睡眠/唤醒和特殊功能仍可能存在前端自身的兼容问题。请在反馈问题时注明前端名称、profile、BaseOS 构建版本和复现步骤。

## 2. 安装 BaseOS

### 2.1 获取测试构建

测试镜像和升级包由专用 GitHub Actions 工作流生成，不是正式 Release：

[打开 RG34XX 多前端测试构建记录](https://github.com/dengzhan007/BaseOS-MultiFrontend/actions/workflows/rg34xx-multi-frontend-test.yml)

进入最新成功的运行记录，在 **Artifacts** 区域下载：

- `baseos-rg34xx-...-multi-frontend-test.img.zip`：完整刷写镜像；
- `baseos-rg34xx-....bosupd`：A/B 系统升级包。

内测期间请确认下载的是 RG34XX 对应构建，不要使用其他 H700 机型的镜像或升级包。

### 2.2 首次安装：刷写完整镜像

1. 关闭掌机，取出 TF1，将 TF 卡接入电脑。
2. 解压下载的 `.img.zip`，得到 `.img` 文件。
3. 使用 balenaEtcher、Rufus 或其他可靠镜像写入工具，将镜像写入 TF1。
4. **确认目标盘是掌机 TF 卡。刷写会覆盖该卡原有分区和数据。**
5. 写入完成后，将 TF1 插回掌机并首次开机。
6. 首次启动会扩展用户数据分区并创建文件系统。等待过程结束，不要断电或拔卡。
7. 首次扩展完成后关机，将 TF 卡接回电脑。此时可见的用户数据分区容量应已扩展。
8. 再将前端文件按第 4 节说明复制到卡内。

不要在镜像写入后自行格式化 TF1 的其他分区，也不要删除 BaseOS 创建的隐藏目录。

### 2.3 已安装本测试版：使用 A/B 升级包

A/B 升级包只适用于已经刷入本项目 RG34XX 七分区 A/B 完整镜像的设备，不能用于从原厂系统直接升级，也不能跨机型使用。

1. 将 `.bosupd` 文件复制到当前活动数据卡的根目录。
2. 如果设备使用 TF2 作为当前前端数据卡，就放在 TF2 根目录；否则放在 TF1 的用户数据分区根目录。
3. 在电脑上安全弹出 TF 卡，再插回掌机。
4. 正常开机，BaseOS 会在启动前检查并应用升级包，完成后自动重启。
5. 升级期间不要断电、拔卡或强制重启。成功提交后，升级包会自动删除。

升级包只更新非活动 rootfs 槽，不会重刷整张卡；游戏、存档、前端程序和用户配置应保留。若升级包被拒绝或写入/校验失败，系统会记录失败原因，并将失败包改名为 `.bosupd.failed`，避免每次开机重复尝试。不要把失败包改回 `.bosupd` 后反复尝试；请先保留日志并反馈。

## 3. 开机与前端选择器

### 3.1 进入选择器

- 开机时按住 **L1 或 R1 任意一个**，即可进入前端选择器。
- 不需要同时按住 L1 和 R1。
- **MENU 键优先用于 USB 大容量存储维护入口**，不要用 MENU 代替 L1/R1。
- 不按组合键时，系统启动已设置的默认前端；如果没有可用前端，则进入诊断/选择界面。

### 3.2 选择器按键

| 按键 | 功能 |
|---|---|
| 方向键 | 移动选择项；列表首尾循环 |
| A | 临时启动当前前端；不会修改默认前端 |
| Start | 将当前前端设为默认并启动 |
| SELECT | 启用/停用当前前端 profile |
| B | 退出选择器，继续使用已有默认项 |
| Y | 修改当前 profile 的显示名称 |
| R1 | 重命名整个前端目录/包身份 |
| L1 | 删除当前托管/兼容 profile 的配置；不等于删除程序目录 |
| X | 进入删除整个前端程序包的确认流程 |
| 左/右（光标在末尾操作行时） | 切换新建 profile 的来源前端 |

列表末尾的 **新建配置…** 用于给已有前端建立另一套独立配置。先将光标移到该操作行，再用左右键选择来源前端，按 A 打开机身虚拟键盘并创建 profile。

### 3.3 删除时要区分两种操作

- **删除 profile/兼容配置**：移除 BaseOS 为该 profile 生成的配置或兼容包装，不会自动删除第三方前端程序目录，也不会删除 Games、Saves 等共享数据。
- **删除整个前端程序包**：按 X 并完成二次确认。此操作会删除对应的前端程序目录或兼容载荷。操作前确认目录中没有需要保留的用户文件。

同一个程序包有多个 profile 时，删除其中一个 profile 不应影响其他 profile；最后一个 profile 被删除时，BaseOS 才会清理该包对应的兼容包装/程序载荷。请勿把“删除配置”和“删除程序”当作同一个操作。

### 3.4 诊断与语言切换

诊断页面提供系统/存储/电池信息、按键测试和 USB 大容量存储入口。按键测试使用掌机印刷按键布局显示输入状态；按 **SELECT + START** 退出按键测试。

本测试版默认简体中文。选择器末尾可切换 English；诊断页可按 L1 切换语言。语言选择保存在系统数据分区，普通 A/B 系统升级不会重置它。

## 4. 安装和管理前端

所有多前端建议放在**同一张当前活动数据卡**的 `Frontends/` 目录中，每个前端使用一个独立子目录：

```text
TF 卡根目录/
├── Games/                       # 统一游戏库
├── Saves/                       # 统一电池存档
├── Frontends/
│   ├── Slot/
│   ├── NextUI/
│   └── spruceOS/
└── .baseos/                     # BaseOS 自动生成的管理数据
```

目录名由用户决定，但建议使用简短、稳定、只包含英文字母/数字/点/下划线/连字符的名称。不要把两个不同前端覆盖到同一个目录中。

### 4.1 普通第三方前端：解压到独立目录

以 Slot、spruceOS 或其他常规前端为例：

1. 在当前活动数据卡根目录创建 `Frontends/Slot/`（名称可自定）。
2. 解压前端发布包。
3. 将前端完整运行目录复制到这个子目录中，保留隐藏文件和隐藏目录。
4. 不要只复制启动文件；前端需要的 `System/`、`.system/`、脚本、资源和库文件应一起保留。
5. 重新启动 BaseOS，打开选择器。系统会扫描并尝试识别前端入口。

示例：

```text
Frontends/
└── Slot/
    ├── System/
    │   └── slot
    ├── ...
    └── （前端发布包中的其他文件）
```

spruceOS 的目录结构可能包含 `spruce/scripts/runtime.sh`；BaseOS 会识别这类启动入口。不要为了符合示例而随意改动前端内部目录结构。

### 4.2 NextUI / MinUI 类卡根载荷前端

某些 NextUI/MinUI 分支把运行路径写死为 SD 卡根目录（例如 `/mnt/SDCARD/.system/`），不能简单地从 `Frontends/NextUI/` 子目录运行。本测试版对此使用卡根载荷兼容方式：

1. 在 `Frontends/NextUI/` 创建目录。
2. 将 NextUI 官方发布包中的 `MinUI.zip`（或符合支持格式的 `*-all.zip`）直接复制进去。
3. 不要手动把 ZIP 解压到卡根，也不要只复制 ZIP 内某个子目录。
4. 如发布包还附带该版本需要的其他文件，请按该前端版本说明一并放入对应目录。
5. 启动时 BaseOS 会按当前设备平台选择归档内对应的 H700 分支，并展开到卡根所需的私有运行目录。

BaseOS 会记录归档状态：归档没有变化时不会每次开机都重新展开；替换成新版归档后会重新处理。卸载时会根据记录清理该前端的私有载荷，但不会把同级的 Games、Saves 等共享目录作为前端载荷删除。

### 4.3 自动兼容与托管包

前端可以通过两种方式出现在选择器中：

- **自动兼容前端**：把原版前端目录放进 `Frontends/<名称>/`。BaseOS 根据明确的启动脚本、目录结构或受支持的 H700 启动二进制识别入口，并在 `.baseos/compat/` 下生成自己的兼容配置。原始前端目录不会被写入 manifest 或 BaseOS 启动脚本。
- **BaseOS 托管前端包**：使用明确的包清单、统一启动脚本和一个或多个 profile 配置。适合需要多个配置实例、希望精确控制启动行为的前端移植项目。

托管包结构示例：

```text
Frontends/
└── example/
    ├── baseos-frontend.conf
    ├── launch.sh
    ├── payload/                 # 可选：前端程序载荷
    └── profiles/
        ├── default.conf
        └── another-profile.conf
```

其中 `baseos-frontend.conf` 描述包级信息，`profiles/*.conf` 描述各自 profile。一个包中的多个 profile 共用程序载荷，但拥有不同的实例目录和用户数据目录。普通用户不需要手工编写这些文件；通常通过选择器的新建配置功能即可创建额外 profile。

### 4.4 更新前端

前端程序更新与 BaseOS 系统升级是两件独立的事：

- 常规前端：按前端自己的发布说明更新对应的 `Frontends/<名称>/` 程序文件，注意不要覆盖或删除其他前端。
- NextUI/MinUI 卡根载荷：替换 `Frontends/<名称>/` 中的 ZIP 归档，再启动让 BaseOS 识别新归档。
- 托管包：按该包的更新约定替换 payload，不要删除 profiles 或 BaseOS 实例数据。

更新前建议备份该前端目录和 `.baseos/instances/` 中相关数据。不要用“重新刷写完整镜像”的方式更新前端。

## 5. 路径映射规则

不同前端可能把同一种数据放在不同目录。例如：

- 前端 A 读取 `Roms/`；
- 前端 B 读取 `ROMs/`；
- 前端 C 读取 `roms/`；
- BaseOS 统一把游戏本体保存在 `Games/`。

路径映射就是在不修改前端源码的情况下，为前端创建它所期待的目录入口，并让该入口指向 BaseOS 的规范目录或该前端自己的私有目录。

### 5.1 规范目录与前端目录名

| 数据类别 | BaseOS 规范目录 | 常见前端目录名/用途 |
|---|---|---|
| 游戏本体 | `Games/` | `Roms/`、`ROMs/`、`roms/` |
| 电池存档 | `Saves/` | `saves/` 或前端指定目录 |
| BIOS | `Bios/` | `BIOS/`、`bios/` |
| 金手指 | `Cheats/` | `cheats/` |
| 遮罩 | `Overlays/` | `overlays/`、`Overlay/` |
| 着色器 | `Shaders/` | `shaders/` |

例如，前端程序原本固定读取 `Roms/`，BaseOS 会在它运行时提供 `Roms -> Games` 的目录映射。前端不需要知道实际游戏库叫 `Games/`，也不需要修改源码。

映射并不意味着复制游戏文件。两个路径最终访问的是同一份数据；删除别名不会删除规范目录中的游戏。

### 5.2 自动识别的目录与私有目录

首次扫描前端时，BaseOS 会检测其目录结构，生成一份路径映射配置。配置保存在：

```text
.baseos/frontend-paths/<frontend-id>.conf
```

这里的 `frontend-id` 是 BaseOS 为前端识别出的 ID，不一定等于界面显示名称。每个前端有自己的映射文件；同一个前端的多个 profile 共用这份映射规则，但 profile 的用户数据仍然独立。

默认规则：

1. `Games/` 和 `Saves/` 是规范共享目录。
2. BIOS、Cheats、Shaders 默认接入对应规范共享目录。
3. Overlays 默认共享；如果前端程序包自身带有 `overlays/` 或 `Overlays/` 目录，则自动生成的配置默认将它设为私有，避免把前端自带素材误当成公共素材。
4. 前端程序目录中的普通顶层目录（包括隐藏目录）默认属于该前端，不会因为名字相似就自动共享。
5. 常见的 `Config/` 或 `config/` 被视为 profile 私有配置；收藏、最近游玩、前端偏好、即时存档等应保持 profile 隔离。
6. 前端自带的模拟器核心不会被覆盖。BaseOS 可以把发现的 H700 libretro 核心补充到共享核心库，并在运行时提供共享核心视图。

### 5.3 `*_target`：让前端继续使用它原来的目录名

路径映射配置中的 `*_target` 表示**前端希望看到的目录名称**，不是要把规范目录改名。

例如，前端源码固定读取单数目录 `Overlay/`，规范公共目录仍然是 `Overlays/`，配置应写：

```ini
overlays_target=Overlay
share_overlays=yes
```

BaseOS 会在前端运行期间提供：

```text
TF 卡根目录/Overlay  ->  TF 卡根目录/Overlays
```

如果另一个前端本来就读取 `Overlays/`，则可使用：

```ini
overlays_target=Overlays
share_overlays=yes
```

两者最终访问的是同一份 `Overlays/` 数据。游戏目录同理，例如 `games_target=Roms` 会让前端继续使用 `Roms/`，而实际数据保存在 `Games/`。

### 5.4 选择性共享：`share_*`

以下开关控制相应素材类别是否接入公共目录：

```ini
share_bios=yes
share_cheats=yes
share_overlays=yes
share_shaders=yes
```

- `yes`：前端看到的是 TF 卡根目录下对应的规范共享目录。
- `no`：前端看到的是当前 profile 自己的私有目录；其他前端不会共享这份内容。

例如，某个前端的 BIOS 需要与其他前端共用时，使用 `share_bios=yes`；如果它需要一套独立 BIOS，则改为 `share_bios=no`。私有 BIOS 会放在该 profile 的实例数据目录中，不会覆盖公共 `Bios/`。

这些设置位于该前端自己的 `.baseos/frontend-paths/<frontend-id>.conf`。自动扫描只在文件不存在时生成默认配置；后续重新扫描不会覆盖用户修改。

### 5.5 可选共享目录：`shared_map`

如果某个前端把素材放在一个 BaseOS 未预设的目录中，例如 `media/`，而你希望它与其他前端共用公共遮罩目录，可以添加 `shared_map`：

```ini
shared_map=media:Overlays
```

格式：

```text
shared_map=<前端程序目录中的源目录>:<BaseOS 规范公共目录>
```

目前允许的公共目标为：

- `Games`
- `Saves`
- `Bios`
- `Cheats`
- `Overlays`
- `Shaders`

可以重复添加多行，例如：

```ini
shared_map=media:Overlays
shared_map=cheatfiles:Cheats
shared_map=firmware:Bios
```

这表示前端运行时分别使用卡根目录下的 `media/`、`cheatfiles/`、`firmware/` 入口访问规范公共目录。源目录必须存在于该前端程序目录中，作为规则校验和前端原目录识别依据；**BaseOS 不会把源目录里的旧文件自动复制到公共目录**。启用规则前，请先备份并手动把需要共享的文件复制到对应规范目录（例如 `firmware/` 中需要共享的 BIOS 文件复制到 `Bios/`）。映射生效后，前端通过该入口读写的是公共目录。未声明的目录仍然保持私有。不要把 `.system/`、程序本体或配置目录随意映射为共享目录。

### 5.6 映射何时生效、会不会搬动文件

- 路径映射在启动对应前端时建立，在前端退出或会话清理时撤销。
- Linux 文件系统支持时优先使用符号链接；FAT/exFAT 不支持符号链接时，使用临时 bind mount 作为兼容方式。
- 映射是目录入口，不是复制或搬移数据。修改映射不会自动合并两个目录中的旧文件。
- 如果卡根目录已经存在同名且非空的真实目录，BaseOS 会保护它，不会强行覆盖；此时该映射可能无法建立，需要用户先备份并手动整理冲突目录。
- 如果只是大小写不同而文件系统不区分大小写，不会重复创建别名。
- 退出前 BaseOS 会清理它自己建立的临时别名/挂载；不会删除前端原始目录或规范共享目录中的文件。

**建议：** 初次使用时先只共享 Games 和 Saves。确认前端确实使用了正确目录后，再逐项开启 BIOS、Cheats、Overlays、Shaders 或自定义共享。不要一开始就把所有目录都设为共享。

## 6. 共享与非共享目录总表

| 内容 | 默认策略 | 说明 |
|---|---|---|
| ROM 游戏本体 | 所有前端共享 | 统一放在 `Games/` |
| 电池存档（例如模拟器生成的 `.sav`） | 所有前端共享 | 统一放在 `Saves/`；前端必须使用对应映射入口 |
| 收藏夹 | profile 隔离 | 不同 profile 可以有不同收藏 |
| 最近游玩 | profile 隔离 | 不同 profile 分别记录 |
| 前端设置/偏好 | profile 隔离 | 避免一个 profile 的设置影响另一个 |
| 即时存档/恢复状态 | profile 隔离 | 不在不同 profile 间混用 |
| BIOS | 默认共享，可关闭 | `share_bios=yes/no` |
| Cheats | 默认共享，可关闭 | `share_cheats=yes/no` |
| Overlays | 默认共享；前端自带目录时默认私有 | `share_overlays=yes/no` |
| Shaders | 默认共享，可关闭 | `share_shaders=yes/no` |
| 其他素材目录 | 默认私有，可选共享 | 通过 `shared_map` 显式加入 |
| 前端程序文件 | 同一 package 的 profile 共享 | 多个 profile 不需要复制多份程序 |
| BaseOS 兼容配置/路径映射 | BaseOS 管理 | 存放于卡内 `.baseos/`，不要手动删除不熟悉的文件 |

注意：共享“电池存档”不代表所有模拟器/核心的存档格式都兼容。不同模拟器可能使用不同文件扩展名、目录结构或命名规则；只有它们最终读写同一份存档文件时，才能实现实际互通。即时存档（state）与电池存档（save）是两种不同数据，不应混为一谈。

## 7. 诊断、USB 存储与日志

### 7.1 USB 大容量存储

可从诊断页面选择 USB 大容量存储入口。开始前先连接数据线，再按界面提示进入维护模式。系统会先卸载准备交给电脑访问的数据分区，再切换为 USB 存储。

传输完成且电脑不再读写时，可以直接拔掉数据线，不再要求先执行系统“弹出”。但**不要在复制、删除或写入过程中拔线**：电脑仍可能有尚未提交的缓存写入，直接拔线可能损坏文件系统。完成文件操作后再断开连接。

### 7.2 日志

如果前端没有启动、返回诊断页面或路径映射似乎未生效，请保留 TF 卡根目录的：

- `baseos-boot.log`：系统启动、前端发现/启动、更新等记录；
- 对应前端的运行日志（如果该前端会生成日志）；
- 失败升级时的 `.bosupd.failed` 文件和 `/data/update/last-failure`（可通过系统诊断/ADB 方式收集）。

反馈时请附上设备型号、BaseOS 版本/构建号、前端目录名、profile 名称、操作步骤和预期/实际结果。请不要只描述“打不开”，尽量指出发生在哪一步。

## 8. 内测注意事项与反馈建议

1. 首次刷写请使用备用 TF 卡，并提前备份。
2. 不要在系统升级、文件复制或 USB 写入过程中断电/拔卡。
3. 不要手动删除 `.baseos/`、`.baseos/instances/` 或 `.baseos/frontend-paths/` 中不熟悉的内容。
4. 不要把两个前端解压到同一个目录，也不要把 profile 当作前端程序目录。
5. 删除整个前端程序前先备份；删除 profile 配置与删除程序包是两种不同操作。
6. 修改路径映射前先备份原目录；不要让同一个目录同时被多个规则以不同方式映射。
7. CI/QEMU 自动测试只能验证构建和部分逻辑，不能代替实机测试。请单独报告未通过的实机项目。

